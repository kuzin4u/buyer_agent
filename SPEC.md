# Персональный AI-агент-закупщик — ТЗ для Claude Code

Редакция 2. Основана на исходном ТЗ («ТЗ_AI-агент-закупщик.docx»), три открытые
развилки закрыты, добавлено правило для чеков без продавца.

Тип агента: **ядро А** (аналитик-советчик). Расширение Б (активный закупщик) —
задел, §9.

---

## 1. Что строим

Агент анализирует историю покупок пользователя (чеки ФНС) и помогает покупать
умнее: формирует корзину под запрос, сравнивает цены и магазины, отслеживает
подорожание, ведёт учёт трат.

Ключевой принцип: агент **не угадывает, а знает** реальные привычки пользователя
из его чеков. Все рекомендации опираются на факты покупок.

## 3. Данные

### 3.1 Боевой источник

Выгрузка чеков из приложения **«Проверка чеков» (ФНС)** в формате JSON.
Пользователь выгружает сам. Значимые поля внутри `ticket.document.receipt`:

```
dateTime            дата и время чека (ISO)
user                продавец (название юрлица) — может быть ПУСТЫМ
retailPlaceAddress  адрес магазина — может быть пустым
totalSum            сумма чека, В КОПЕЙКАХ
items[]             позиции:
   name             название товара (грязное)
   price            цена за единицу, В КОПЕЙКАХ
   quantity         количество (дробное для весовых)
   sum              сумма позиции, В КОПЕЙКАХ
```

### 3.2 Датасет в пакете

`data/receipts.json` — тот же материал в уже развёрнутом виде: копейки переведены
в рубли, названия продавцов сведены к читаемым. Схема полей — `docs/DATASET.md`.

Парсер боевого ФНС-JSON и загрузчик этого датасета должны сходиться в одну
внутреннюю модель. Пиши слой ввода так, чтобы источник подменялся.

### 3.3 Настройки пользователя (хранить локально)

- Обязательные и исключённые продукты корзины.
- Оценки магазинов: качество и обстановка (звёзды 1–5).
- Основной магазин по умолчанию, целевой бюджет.
- Флаг `include_candidates` (см. §5.1).

Хранение: localStorage (веб) или файл/БД (бот). Данные не покидают устройство
пользователя.

## 4. Развилка 1 закрыта: два уровня атома

Исходное ТЗ сводило названия к товарным группам («сметана»). Демо-анализ шёл на
уровень SKU (бренд + жирность + фасовка) и был прав в том, что для динамики цен
сравнивать надо одинаковое с одинаковым. **Нужны оба уровня, и они не
взаимозаменяемы.**

**Группа** (`category`) — «сметана», «молоко», «фарш». Единица учёта потребности:
пользователь думает «нужна сметана», а не «нужна сметана Viola 23% 315 г».

**SKU** (`sku_key`) — кортеж `группа · бренд · жирность/сорт · фасовка`.
Единица учёта цены: только внутри SKU цена сопоставима во времени и между
магазинами.

| Функция | Уровень | Почему |
|---|---|---|
| 2.1 Профиль предпочтений | оба | состав корзины — группы; любимая марка внутри группы — SKU |
| 2.2 Корзина «как обычно» | группа, с типичным SKU | берётся группа, подставляется самый частый SKU |
| 2.3 Корзина под бюджет | группа | замена дорогого SKU на дешёвый внутри группы — главный рычаг экономии |
| 2.4 Что давно не покупал | группа | «давно не брал сметану», а не конкретную банку |
| 2.5 Динамика цен | **только SKU** | смена фасовки или марки маскирует реальный рост |
| 2.6 Сравнение магазинов | **только SKU** | иначе сравниваются разные товары |
| 2.7 Рейтинг магазина | SKU → агрегат | ценовой ранг считается по общим SKU |
| 2.8 Контроль трат | группа и отдел | деньги удобнее смотреть крупно |

Правило: **любое сравнение цен — внутри одного SKU. Любой выбор состава — на
уровне группы.**

Бренд может не распознаться — это нормально и SKU не ломает: жирность и фасовка
сами по себе различают позицию. В демо самый частый SKU сметаны — `— · 25% · 300 г`,
36 покупок. Нераспознанный бренд пишется как `—`.

## 5. Развилка 2 закрыта: единица цены

Исходное ТЗ требовало ₽/кг и запрещало ₽/упаковку. Демо считало ₽/упаковку.
Оба правы на своём уровне:

- **Уровень SKU** — фасовка постоянна по определению, поэтому цена за упаковку
  сопоставима. Считать и хранить **обе меры**: `₽/упаковку` показывать пользователю
  (эту цифру он видит на полке), `₽/кг` использовать для сравнения SKU между собой
  и для расчёта корзины.
- **Уровень группы** — фасовки разные, цена за упаковку бессмысленна.
  **Только ₽/кг или ₽/литр**, медианой.

Извлечение фасовки, весовые товары, исключения — `config/normalization.json`.
Три вещи, о которые спотыкается наивная реализация (все три встречаются в данных):

1. `ПАКЕТ ЛЕНТА СРЕДНИЙ МАЙКА 12КГ` — это грузоподъёмность пакета, а не вес товара.
   Позиции из `excluded_items` до извлечения фасовки не доходят.
2. `СМЕТАНА 25%300Г` — число после `%` это фасовка, но само `25` — жирность.
   Жирность вырезается до применения правил фасовки.
3. `ПИВО КЕРСАРИ СВ 0,45` — литраж без единицы измерения. Правило работает
   только для напитков, иначе будет ловить артикулы.

Если фасовка не извлеклась и товар не весовой — позиция участвует в контроле трат,
но **не участвует** в динамике цен и сравнении магазинов. Молча выбрасывать нельзя:
доля таких позиций выводится в диагностике.

Агрегат — **медиана**, минимум 3 наблюдения в срезе. Меньше — это шум, а не тренд.

### 5.1 Гомоглифы — обязательная первая операция

Касса подмешивает латиницу в кириллические названия: в данных реально есть
`ПАKЕТ ПОKУПАТЕЛЬСKИЙ` и `KЕФИР 3,2%` с латинской `K`. Без замены один товар
распадается на два SKU.

Но замену надо делать **пословно и только в словах, где есть кириллица**.
Сплошная замена ломает честно латинские названия: `PATERRA` → `РАТЕRRА`,
`DEL.` → `DЕL.`, `R.SP.` → `R.SР.`. Это тоже проверено на данных — в первом
прогоне валидатора эти три позиции всплыли как нераспознанные именно из-за
сплошной замены.

## 6. Развилка 3 закрыта: словарь брендов

Касса режет бренд до 4–8 символов: `ВКУСН` → Вкуснотеево, `ВОЛОГ` → Вологодская,
`САВУШ` → Савушкин, `БР-ЛИТ` → Брест-Литовск.

Это **накапливаемый вручную актив, а не разовая задача**. Требования к коду:

- словарь читается из `config/brands.json`, не зашивается в код;
- у каждого правила есть поле `confidence`: `confirmed` показывается как есть,
  `probable` требует подтверждения пользователем перед показом в интерфейсе
  (в файле такие помечены — например, `СВЕТ.` / `СВИТ.` могут оказаться разными
  брендами, и тогда правило разведёт SKU неверно);
- агент выводит **топ-20 нераспознанных префиксов по числу покупок** — это очередь
  на пополнение словаря, и пополнять её должен пользователь одним кликом из интерфейса.

## 7. Дыра в фильтре закрыта: чеки без продавца

196 чеков (336 тыс ₽, 2017–2020) пришли с пустым полем продавца и пустым адресом —
**четвёртое место по деньгам во всей выборке**. Внутри в основном Избёнка/ВкусВилл
и Мясновъ: молоко, кефир, творог, сметана, плюс немного АЗС. Фильтр по имени
магазина теряет их целиком.

Правило (`shops.json` → `unknown_resolution`): если продавец пуст или не совпал ни
с одним правилом, чек классифицируется **по составу позиций** — по доле суммы,
попавшей в товарные группы. Порог 0,6. Прошедшие получают магазин `Не определён`.

Такие чеки участвуют в контроле трат и в динамике цен по SKU, но **не участвуют в
сравнении магазинов** — сравнивать не с чем.

Три яруса магазинов в `shops.json`:

- `food_core` — 10 сетей, воспроизводят контрольные цифры ТЗ. Всегда включены.
- `food_candidate` — похоже на продуктовое, но объём мал или юрлицо неоднозначно.
  **По умолчанию выключено**, включается флагом. Отдельного внимания стоит
  «Агроаспект» — это юрлицо сети Перекрёсток, и при включении его чеки сольются
  с уже имеющимся Перекрёстком.
- `non_food` — АЗС, связь, ЖКХ, стройка, аптеки. Из ценового анализа исключены
  всегда, но в контроле трат (функция 2.8) остаются: это тоже деньги пользователя.

## 8. Функции ядра А

Восемь сценариев. Уровень атома для каждого — таблица в §4.

**8.1 Профиль предпочтений.** Строится автоматически. Постоянная корзина (топ групп
по числу чеков, с учётом обязательных позиций пользователя), частота покупки каждой
группы, типичный SKU внутри группы, основной магазин и его доля в тратах, средний
чек, категории трат и их доли.

**8.2 Корзина «как обычно».** Набор из постоянной корзины под средний чек или
заданный период (неделя/месяц).

**8.3 Корзина под бюджет.** «Уложись в N ₽». Приоритет — регулярным группам.
Главный рычаг — замена дорогого SKU на дешёвый внутри той же группы; показывать
пользователю, чем именно заменили.

**8.4 Что давно не покупал.** Сравнение частоты покупки группы с датой последнего
появления. Если группа берётся часто, но давно не появлялась — предложить докупить.

**8.5 Динамика цен.** Рост ₽/кг по годам, в рублях и процентах, **только внутри
SKU**. Абсолютный рост (₽) — приоритетная мера, процент — вспомогательная.
Сортировать по |рост_абс|, показывать обе меры.

**8.6 Сравнение магазинов.** Медианная ₽/кг каждого SKU корзины по магазинам.
Где каждый дешевле, и «умная корзина» — маршрут экономии против покупки в одном
магазине.

**8.7 Выбор магазина: цена + качество + обстановка.** Ценовой ранг из чеков.
Качество продуктов и общая обстановка — ручные оценки пользователя (звёзды 1–5),
этих данных в чеках нет. Итог комбинирует ранг и обе оценки; если оценок нет —
только цена.

**8.8 Контроль трат.** По годам, месяцам, магазинам, отделам и группам.
Выявление, где траты растут. Сюда входит `non_food` — это тоже расходы.

### 8.9 Понимание запросов — гибрид

**Базовый слой (без ЛЛМ, всегда работает):** кнопки типовых сценариев + разбор
параметров regexp'ом (число = бюджет, название продукта, период). Работает офлайн,
без ключей.

**Умный слой (с ЛЛМ, опционально):** свободные формулировки → разбор намерения →
вызов функций ядра, объяснение результата человеческим языком.

**Архитектурное требование, не подлежащее смягчению:** ЛЛМ — надстройка над
детерминированным ядром, не замена. Все числа считает ядро — точно и
воспроизводимо. ЛЛМ разбирает запрос и объясняет результат, но **не считает и не
выдумывает цифр**. Ключ ЛЛМ — на стороне сервера (прокси), не в клиенте. Без ключа
агент работает на базовом слое.

### 8.10 Интерфейс и платформа

Платформу выбираешь ты, с обоснованием. Требования к любой:

- чат-подобное взаимодействие (запрос → ответ с корзиной/аналитикой) + кнопки
  быстрых сценариев;
- визуализация: корзина с суммой и экономией, графики динамики цен по SKU, таблицы
  сравнения магазинов;
- настройки: обязательные продукты, оценки магазинов, бюджет, флаг кандидатов;
- панель диагностики: доля нераспознанных позиций, топ префиксов без бренда, топ
  названий без группы — с возможностью пополнить конфиг прямо оттуда.

Рекомендация к рассмотрению: общее ядро (JS или Python) + два интерфейса — веб
(демонстрация, как `reference/sku-demo-smetana.html`) и Telegram-бот (для
ежедневного использования). Можешь предложить иное с обоснованием.

## 9. Расширение Б — активный закупщик (на будущее)

Не для первой версии. Ядро проектировать так, чтобы это добавлялось без
переписывания: оформление заказа (ссылки на товары / API магазина), автонапоминания,
отслеживание цен с уведомлением о подорожании регулярного SKU.

Ограничение реальности: маркетплейсы и сети закрыты, встроить автозаказ внутрь их
сайта нельзя. Реальные пути — официальный API магазина, ссылки на товары, или свой
канал продаж. Это внешние интеграции, вне кода ядра.

## 11. Резюме

Вход: JSON чеков ФНС либо `data/receipts.json`.
Конвейер: гомоглифы (пословно) → регистр → исключения → нормализация магазина
(3 яруса + разбор по составу для безымянных) → категоризация в группу →
извлечение фасовки → сборка SKU → медианы ₽/кг и ₽/упаковку → профиль.
Сравнение цен — только внутри SKU. Выбор состава — на уровне группы.
Понимание запросов — гибрид, числа только из ядра.
Конфиги — файлы, не код; словарь брендов пополняется пользователем.
После каждой правки конфига — `python3 validate.py`.
