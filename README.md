# Пакет для Claude Code: персональный AI-агент-закупщик

Всё, что нужно, чтобы начать писать код: спецификация с закрытыми развилками,
реальный датасет и конфиги, проверенные на нём.

## С чего начать

```bash
python3 validate.py                        # покрытие по датасету
python3 -m unittest discover -s tests      # 321 тест, эталон и функции ядра
```

Веб-оболочка — основной интерфейс (`docs/DECISIONS.md` Р-1):

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
.venv/bin/python -m web                    # http://127.0.0.1:8000
```

Все восемь функций доступны из браузера, плюс настройки §3.3 и панель
диагностики. Базовый слой §8.9 работает офлайн и без ключей: кнопки типовых
сценариев и разбор запроса регулярками — «уложись в 2000», «что давно не
покупал», «траты по отделам». Непонятый запрос так и называется непонятым, а не
угадывается.

Панель диагностики (`/diagnostics`) — не отладка, а продолжение главной функции.
Главный вопрос «варианты моей корзины в разных магазинах» упирается в покрытие:
сравнимых товаров 25, разводится 4 строки корзины из 8. Поэтому после каждого
пополнения словаря печатается вся цепочка — распознана группа → определена
фасовка → распознан бренд → товар сравним между магазинами → **строка корзины
разводится**, — и эффект меряется прогоном, а не предсказывается: правило бренда
расщепляет смешанный ключ, и осколки могут не добрать наблюдений. Правило, не
сдвинувшее ответ, так и помечается.

У каждой неразведённой строки написано, чего не хватает, и задания отделены от
фактов: «марка не распознана» правится прямо из очереди, а «вы берёте это только
в одном магазине» не правится ничем — выдавать такое за задание значит гонять
человека за невозможным. Если типичный товар группы сравнить не с чем, а вторая
ваша марка в той же группе сравнима и берётся сопоставимо часто, цена берётся по
ней — с явной пометкой, по какой (`docs/DECISIONS.md` Р-25).

Ядро от оболочки не зависит и работает на одной стандартной библиотеке: полный
прогон тестов проходит без установки чего-либо, тесты веба при этом пропускаются.

Функции ядра А на уровне группы — уже работают:

```bash
python3 cli.py profile                     # 8.1 профиль предпочтений
python3 cli.py basket --period week        # 8.2 корзина «как обычно»
python3 cli.py basket --budget 2000        # 8.2 то же под заданную сумму
python3 cli.py budget 2000                 # 8.3 уложиться в сумму: замены, потом выброс
python3 cli.py budget 15500 --period month # 8.3 то же на месяц
python3 cli.py lapsed                      # 8.4 что давно не покупал
python3 cli.py prices                      # 8.5 динамика цен внутри SKU
python3 cli.py venues                      # 8.6 где что дешевле
python3 cli.py venues --basket week        # 8.6 умная корзина: маршрут экономии
python3 cli.py choose                      # 8.7 выбор магазина
python3 cli.py spending --by dept          # 8.8 контроль трат
python3 cli.py spending --growth --by group   # где траты растут
```

CLI остаётся рядом с вебом: им удобно проверять ядро и сравнивать вывод
построчно. Бот — С6. Числа считает ядро, обе оболочки только печатают.

Прогон применяет конфиги к датасету и печатает покрытие. Занимает секунды, ничего
не пишет. Если цифры совпали с `docs/DATASET.md` — пакет цел, можно читать
`SPEC.md`. Тесты сверяют вывод с `docs/BASELINE.txt` построчно, так что регресс
виден сразу. У ядра внешних зависимостей нет, только стандартная библиотека;
у веб-оболочки они есть и перечислены в `requirements.txt`.

## Что изменилось против исходного ТЗ

Семь решений, принятых после сверки ТЗ с реальными данными. Подробно — в `SPEC.md`,
разделы 4–7, и в `docs/DECISIONS.md`.

1. **Два уровня атома, а не один.** Группа («сметана») — для состава корзины,
   бюджета и напоминаний. SKU (бренд·жирность·фасовка) — для цены, динамики и
   сравнения магазинов. Любое сравнение цен только внутри SKU.
2. **Единица цены зависит от уровня.** На SKU — обе меры: ₽/упаковку показывать
   пользователю, ₽/кг считать. На группе — только ₽/кг.
3. **Словарь брендов — конфиг, а не код.** Пополняется пользователем; правила с
   `confidence: probable` требуют подтверждения.
4. **Чеки без продавца классифицируются по составу позиций.** Их 196 на 336 тыс ₽ —
   четвёртое место по деньгам, и фильтр по имени магазина терял их целиком.
5. **Замена внутри группы — только для фасованного товара.** Главный рычаг 8.3 —
   заменить дорогой SKU на дешёвый в той же группе. Для весового товара это
   невозможно: у него различитель — само название (§5), поэтому «дешевейшее в
   группе» предлагало заменить лук на капусту, а свиные рёбра на свиные ноги.
   Формально дешевле, для человека — другой ужин. Подробно в `docs/DECISIONS.md`
   Р-22.
6. **Одна модель на четыре агента, горизонт параметром.** Закупщик — частный случай
   общей операции «профиль × каталог». Слои `core` / `profile` / `matching` / `adapters`
   разводятся сразу, но три адаптера сейчас НЕ пишутся — см. SPEC §8.10 и §9.
7. **Три правила фасовки выведены из самих чеков** — дробное количество, число перед
   «ШТ», голое число в конце. Подняли покрытие с 40,9% до 58,6% без внешних источников.

## Конфиги — рабочий материал, а не фон

Они не финальные и не должны быть. `validate.py` печатает две очереди на
пополнение: топ нераспознанных названий (→ `categories.json`) и топ префиксов без
бренда (→ `brands.json`). Покрытие 75,6% по группам и 58,6% по фасовке — это
рабочая база, а не потолок; каждое добавленное правило проверяется тем же прогоном.

Эти же две очереди должны быть видны пользователю в интерфейсе агента — с
возможностью пополнить словарь одним кликом. Это не диагностика для разработчика,
а часть продукта: словарь брендов будет пополняться всё время жизни агента.

## Чего в пакете нет

- Свежих чеков — выгружает пользователь из «Проверка чеков» (ФНС).
- Ключа ЛЛМ — вставляется пользователем в серверный прокси. Без него работает
  базовый слой, и это не урезанный режим: все восемь функций считаются полностью.
- Телеграм-бота — С7. Он не будет хранить состояние (`docs/DECISIONS.md` ОА-1).

## Статус данных

`data/receipts.json` — реальная история покупок за девять лет, владелец решил
публиковать её вместе с кодом. Ограничений на размещение в публичном репозитории
нет: датасет можно коммитить, разворачивать на публичном хостинге и показывать
в демо.

Что практически из этого следует для кода: не нужен слой обезличивания, не нужны
`.gitignore`-исключения под `data/`, демо-режим может работать прямо на боевом
датасете — отдельный синтетический набор для показа не требуется.

Настройки пользователя (§3.3 SPEC) — другое дело: оценки магазинов, обязательные
продукты и бюджет живут локально у каждого пользователя и в репозиторий не
попадают.
